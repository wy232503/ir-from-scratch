# ir-from-scratch

从零手写的倒排索引内核。不训练模型，不依赖检索库。本项目是铁路 RAG 平台的检索内核部分，检索结果用于给出规程原文供人工核对。

## 这是什么

把「文档 → 词」翻转成「词 → 文档列表」，让查询从「扫全部文档」变成「只碰命中的列表」。

目标是完整实现一个检索内核——倒排索引、布尔检索、后面的打分与压缩——每一层都自己写，并且知道自己为什么这么设计。不含界面、模型训练、框架封装，这些属于外壳层。

## 现在能做什么

玩具语料 5 篇英文文档，全部验收通过：

- `index_build` — 建倒排表与文档频率
- `intersect` — 双指针求交，只接受 docID 整数列表
- `multi_and` — 多词 AND，按 df 升序排，减少中间结果
- `search` — `tokenize` 然后 `multi_and` 的接缝

后续路线：接真实语料 → BM25 打分 → 索引压缩 → 短语查询。

## 怎么跑

```bash
python -X utf8 py_index_build_one_pass.py
```

预期输出最后三行：

```
全部对上
multi_and 全过
求交顺序: ['delay', 'signal', 'train']
```

任何一行没出现，说明断言在它之前已经断了——这三行是刻意设计的诊断分界线。

## 设计上的三个决定

**1. `search` 只做两件事：`tokenize`，然后 `multi_and`。**

排序、原文回显、兜底一律不进来。它存在的全部意义是一个接缝：换分词器（比如从空格切分换成 jieba）时只改 `tokenize`，下面三层一个字不动。

**2. `intersect` 只接受 docID 整数列表，断言写在函数开头。**

放在调用处只能护住那一次调用，`multi_and` 内部的调用会直接绕过去。实测把 posting 元组列表直接传进去，会静默漏掉文档。

**3. `post` 必须按 docID 升序，这是正确性前提，不是性能优化。**

双指针求交依赖有序，不排序的话结果错误，而不是变慢。

## 三个踩过的坑

**GBK 编码崩在断言链中间。** 脚本里原本有个 `✓`，在 cmd.exe 或输出重定向时抛 `UnicodeEncodeError`。危险之处在于它崩在断言链中间——后面的断言一条都跑不到，看起来像「已经跑过了」。中文 Windows 上任何非 ASCII 装饰符号都可能这样，用 `-X utf8` 或者重定向 stdout。

**元组比较会静默漏文档。** `intersect([(1,1),(2,3)], [(1,1),(2,1)])` 返回 `[(1,1)]`——doc 2 两边都有却被跳过。因为 `(2,3) != (2,1)` 且 `(2,3) < (2,1)` 为假，于是 j 前进、i 卡死。玩具语料上所有 tf 都是 1，这个 bug 根本测不出来。根因是两种数据形态混用，解法是把契约挡在边界外。

**`res = list[0]` 少写一个 `s`，不报错。** Python 3.9+ 里 `list` 是可下标泛型，这行静默返回一个 `GenericAlias` 对象，直到传给 `intersect` 读元素时才抛 `TypeError: There are no type variables left in list[0]`。报错行号是症状不是病灶——出错行不是自己改的那行时，往上溯两三行查这个变量从哪来。

## 下一步

接 462 条真实铁路规程语料，jieba 分词后重建索引。验收四条：

1. 文档数正好 462
2. 词条数与平均 df 合理（原始分词实测 vocab=4279、avg df=5.62；去停用词、丢单字后预计 3500 上下）
3. 三个真实短查询返回非空且条号合理
4. 四个内核函数零改动

第 4 条是接缝设计的现场验证——如果为了接语料改了内核，说明接缝失败了。

## 辅助脚本

`_cfdf_stats.py` 对语料算词频（cf）与文档频率（df），用来数据驱动地生成停用词表，而不是手写一张表。需要自备 JSON 语料，结构为 `{"articles": [{"article_no": ..., "text": ...}, ...]}`：

```bash
python -X utf8 _cfdf_stats.py path/to/corpus.json
```
